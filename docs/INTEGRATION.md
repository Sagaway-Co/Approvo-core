# 接入指导手册

> [`GETTING_STARTED.md`](GETTING_STARTED.md) 讲的是「怎么把 approvo 跑起来」。
> 本文讲的是「怎么把**你自己的仓库**接上去，并且**知道每一步是真的成了**」。
>
> 本文每一条「坑」都对应一次真实事故。删掉某条约束之前，先找到那次事故为什么不会再发生。

---

## 0. 接入前先定三件事

| 问题 | 说明 |
|---|---|
| **谁能批准？** | 审批人 = 审批群的当前成员。**拉群 = 授权，踢群 = 撤权**，不改配置。所以这个群的成员名单就是你的授权名单，要当权限系统来管。 |
| **批准后谁去部署？** | 推荐 `method: github`：approvo 只调受限发版仓的 `workflow_dispatch`，**自己不持任何集群凭证**。真实凭证只存在于那个受限仓里。 |
| **失败时要响还是要静？** | 一律 fail-close。approvo 不可达 ⇒ 业务仓 workflow 失败 ⇒ 没有审批就发不出去。**绝不要 `|| true`。** |

## 1. 五步接入

### 第 1 步 · 在 approvo 侧登记这个应用

`config.yaml` 的 `releases` 加一项（字段含义见 [`CONFIGURATION.md`](CONFIGURATION.md)）：

```yaml
releases:
  my-app:                     # release_key，业务仓 curl /release 时的 repo 字段
    project: MY-PROJECT
    method: dryrun            # 🔴 先用 dryrun，跑通链路再换真部署
    image_repo: registry.example.com/my-org/my-app
    source_repo: my-app       # 用来生成"变更清单"（PR + 直接提交 + 作者）
```

切到 `method: github`（真部署）时还要显式写两处，**漏了会被拒绝而不是取默认值**：

```yaml
    github:
      owner: my-org
      repo: my-deploy-repo
      workflow: deploy.yml
      env: qa                 # 🔴 必填。曾经默认 "prod" —— 漏写就静默打到生产
    deploy:                   # 🔴 真实部署目标（卡片显示 + 决定往哪签部署凭据）
      cluster: qa             # 不配就不发券、流水线明确失败；approvo 不猜 namespace
      namespace: qa-namespace
```

**判据**：`GET /healthz` 返回 200，且 `/admin` 页面能看到这个 release_key。
**不要**只看容器起来了 —— 进程起得来 ≠ 配置被读进去了。

### 第 2 步 · 业务仓配两个 secret

| secret | 值 |
|---|---|
| `RELEASE_GATE_URL` | approvo 的地址，**必须 https**（见坑 ①） |
| `RELEASE_GATE_TOKEN` | 与 approvo 的 `RELEASE_TOKEN` 一致 |

🔴 **共享 token 不构成身份**：它在 org 里人人可得，无法归因到人。所以凡"谁申请的"会影响后果的接口，approvo 另外用 IM 的 user_id + 群成员校验，而不是只认这个 token。

### 第 3 步 · 复制 workflow 模板

把 [`examples/caller-workflows/build-and-request-approval.yml`](../examples/caller-workflows/build-and-request-approval.yml) 放进业务仓。

🔴 **请照抄，尤其是那两道检查**（https 门禁 + `%{http_code}` 判据）。它们看起来啰嗦，但删掉其中任何一条都会让关卡变成"假的"。

### 第 4 步 · 用 dryrun 跑通整条链路

打一个 tag，然后确认：申请卡片送达 → 点通过 → 结果卡片送达。

**判据**：
- workflow 日志里有 `✅ 审批已提交 (HTTP 2xx)`——**不是**"命令没报错"
- 审批群真的收到卡片——**不是**"接口返回 200"（两者可以不一致：卡片发送是异步的）

### 第 5 步 · 切真部署

`method` 从 `dryrun` 改成 `github`（或 `kubectl` / `helm`），填好目标。

**判据**：部署后去看**目标对象的状态字段**（如 `status.readyReplicas`），而不是部署命令的返回码。

## 2. 判据对照表（本文最该记的一页）

| 步骤 | ❌ 不要用这个当判据 | ✅ 要用这个 |
|---|---|---|
| 提交审批 | `curl` 退出码 | HTTP 状态码是 2xx |
| 服务健康 | 容器 Running / 健康检查绿 | 目标功能真的跑了一次 |
| 部署完成 | `rollout status` 说 success | `status.readyReplicas` == 期望值 |
| 配置生效 | 配置文件里写了 | 从运行中的进程把值读回来比对 |
| 改了密钥 | Secret 已更新 | **Pod 已重建**，且容器内的值指纹符合预期 |
| 权限收窄 | 策略文档看着对 | 用**目标身份**实测：该通的通、该拒的拒 |
| 没有报错 | 日志里没有 error | 先证明这个探针在出错时**会**报错 |
| 端点能不能被公网调到 | 网关返回 404 就以为路径不存在 | 对照 `/release`（422=能到应用）与 `/no-such-path`（404），分清是**没放行**还是**没实现** |
| 卡片说"无数据库变更" | 卡片上没有红标 | 卡片必须区分"无变更"与"**无法判定**"——查不到时它会明说 |
| 同一个 tag 发第二个环境 | 返回 200 就当成功 | 返回体里**不是** `{"skipped":"already deployed"}`（判重按 repo+tag+**stage**） |

## 3. 坑（每条都来自真实事故）

### ① `curl -f` 对 3xx 返回 0 —— 假的 fail-close
网关迁移后 `GATE_URL` 还是 `http://`，服务端 301 跳 https。`-f` 只对 ≥400 失败，**3xx 一律返回 0**。
后果：**一整天所有 workflow 全绿，审批一次都没送达**。
⇒ 判据落在 `%{http_code}`；并且强制 https（http 会在 301 之前的第一跳就把 token 明文发上网络）。
⚖️ **"假的 fail-close" 比没有 fail-close 更危险，因为它让你相信关卡在生效。**

### ② 改完 Secret 必须**重建 Pod**，不是重启容器
`secretKeyRef` 和 `envFrom.secretRef` 注入的环境变量**只在 Pod 创建时**求值。
CrashLoopBackOff 反复重启容器，读到的还是同一份旧值。
⇒ `kubectl delete pod` 或 `rollout restart`。判据是**容器内取值的指纹**，不是 Secret 里的内容。

### ③ 缺省值绝不指向生产
把 `cluster` 之类字段的默认值写成生产环境，等于"少传一个字段就打到生产"。
⇒ **缺字段就拒绝，不猜**。目标一律走配置白名单（`viewer_targets`），而不是信任请求体。

### ④ 同一能力的多个入口必须共用同一份判据
只加固一条 = 没加固，绕过者只会走松的那条。
（真实形态：卡片按钮加了目标白名单，而同功能的 HTTP 接口没加；
或者签只读凭证有白名单，而**破坏性更强**的"改 Secret"反而没有 —— 判据倒挂。）

### ⑤ 短期凭证用完即毁，长期密钥必须有**可访问的权威源**
把"用完即毁"错用在长期共享密钥上，会逼着人反复动用超级权限去取一个普通密钥。
⇒ 长期密钥放在权威存储里，用受控通道取用。

### ⑥ 空输出 / 跳过 比报错更危险，因为它长得像成功
`2>/dev/null` 吞掉 stderr、heredoc 顶掉 stdin、CI 用例全被 skip、变量取值为空后拿去比较……
都会让"什么都没发生"看起来像"一切正常"。
⇒ **先断言装置真的产出了东西**，再看它的结论。

### ⑦ 探针必须先自证
要下"被拒/为空/没差异"这类**阴性结论**之前，先证明这套探针在**阳性**情况下会给出阳性。
例：轮换共享密钥前，先用旧密钥拿到一次成功、用乱写的密钥拿到一次 401 —— 确认判据两种情况都说真话，再动手。

### ⑦.5 "兜底"会掩盖"根本没接上"
按项目名猜 namespace、未命中的 stage 回落顶层配置、拿不到 env 就默认 prod ——
这类兜底让**一部分**应用端到端跑通，于是"配置没接上"这件事在它们身上看不出来，
直到另一部分应用发版时突然全挂。
⇒ 宁可**大声失败**：配漏了就拒绝执行，不要"也许这是设计"。

### ⑧ 写进文档 ≠ 落进代码
一条"正确写法"曾被写进内部手册，而**所有仓库一个都没改**，坑一直敞着。
⇒ 规则类修复要附一份「已推平到哪些仓」的清单，并定期复核。

## 4. 安全约束

- **密钥不要贴进对话 / 文档 / git**。传值一律：`read -rs` 粘贴 → 写入 600 临时文件 → 管道或 `--from-file` 传入 → `shred -u` 销毁。
  `--from-literal=` 会把值写进 argv，同机 `ps` 可见。
- 🔴 **错误处理路径也要遵守同样的约束**。曾有人在正常路径小心地不打印 token，却在 `|| { cat file; }` 的失败分支把它整个吐了出来 —— **错误分支恰恰是最少被审视的地方**。
- 🔴 **审批人看不懂的审批 = 没有审批**。卡片必须让人看出这次改动会让集群发生什么。
- **AI / 自动化代执行也要用真实身份**，不要用 `bot` 这类无法归因的字符串。

## 5. 回滚

| 回滚什么 | 怎么做 |
|---|---|
| 镜像版本 | 重新发一个旧 tag（不要删 tag —— 删 tag 不释放版本号，会造成"同号不同码"） |
| 配置 | 用旧 commit 重新 apply |
| 密钥 | 换之前先把现值备份到 600 文件；换完留一个可回退窗口再销毁旧值 |
